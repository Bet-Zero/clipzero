# NBA PBP Fallback Discovery Return Package

## 1. Executive Summary

**Verdict:** `FALLBACK_INCONCLUSIVE`

The tested failure is not a total CDN outage. The current ClipZero `CDN_HEADERS` profile in `apps/api/src/lib/nba.ts` sends only `Accept` for CDN requests (`apps/api/src/lib/nba.ts:381-392`), and that request profile now returns broad `403 text/html` responses for the tested liveData scoreboard, play-by-play, and boxscore paths. The same CDN play-by-play and boxscore URLs returned real JSON for multiple game IDs when sent with browser-like headers, which means the upstream data is still present for at least part of the surface.

The fallback path could not be proven safe from this environment. Both candidate stats play-by-play endpoints (`playbyplayv3`, `playbyplayv2`) timed out with zero bytes received using headers equivalent to `STATS_HEADERS` (`apps/api/src/lib/nba.ts:366-378`). A follow-up `videoeventsasset` probe using a real made-shot `actionNumber` derived from the accessible CDN JSON for `0042500204` (`GameEventID=14`) also timed out. That hit the prompt's stop condition: all candidate fallback endpoints failed by timeout before ID compatibility or video URL resolution could be validated.

The present risk is therefore not "NBA data disappeared" but "the current request profile is no longer sufficient, and the unimplemented fallback path cannot be validated from this host." Any stats-based fallback would currently be a blind change with unproven event-ID compatibility and cache-schema risk.

## 4. Clip Mapping Risk

- **Are fallback event IDs compatible with `videoeventsasset`?** Not proven. The only verified contract in this repo is that ClipZero currently sends `GameEventID = actionNumber` from CDN play-by-play (`apps/api/src/lib/nba.ts:620-637`, `apps/api/src/index.ts:1381-1384`).
- **Could the fallback create wrong clip mappings?** Yes. `getFilteredActions()` explicitly remaps steals and blocks to the **previous** action number (`apps/api/src/lib/nba.ts:442-444`), which means a fallback that renumbers events, omits companion events, or exposes defensive events differently could silently attach the wrong video to a clip.
- **What validation is needed before serving fallback-based clips?** At minimum: live-sample validation for made shot, missed shot, turnover, and steal/block; confirmation that fallback event IDs produce the expected `videoeventsasset` payload for the same semantic action; and a manual spot-check that descriptions and video content still align after normalization.

## 5. Cache Interaction

- **Can the current play-by-play cache store fallback-normalized results without schema risk?** Not safely from this evidence set. `getCachedPlayByPlay()` persists successful upstream `RawAction[]` payloads directly under the `play-by-play` cache key (`apps/api/src/index.ts:364-390`). A fallback source would need to match the current `RawAction` contract exactly before being stored under that same key.
- **Should the cache key include source/version?** Yes, if a fallback is ever added. Today the persistent key is effectively just `gameId` inside the `play-by-play` bucket (`apps/api/src/index.ts:377-390`). Mixing CDN-native and fallback-normalized payloads under one key would create schema and provenance ambiguity.
- **Does the existing 30-day play-by-play policy remain safe?** It remains safe only for a validated, stable source. The docs set `play-by-play` to 30 days (`docs/cache-guide.md:38-44`), which is reasonable for known-good historical data but too sticky for unverified fallback-normalized payloads.
- **Should successful fallback data be cached?** Only after source/version separation and schema validation. Otherwise a bad normalization could persist for 30 days.
- **Should 403/error responses ever be cached?** No. Current play-by-play logic only persists on successful upstream fetch (`apps/api/src/index.ts:388-390`), and current video-asset logic intentionally avoids persisting failures (`apps/api/src/index.ts:333-340`). That safety property should be preserved.
- **How do cache layers behave today?** The docs describe an API in-memory layer plus persistent disk caches (`docs/cache-guide.md:23-31`). `/clips/game` also refuses to response-cache unresolved clip payloads (`apps/api/src/index.ts:1432-1434`), which is a useful guard against locking in partial video failures.
